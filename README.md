# 台股淨成長 5% 預測系統

每天掃描台股（自選股 ∪ 成交金額排行前 300），排序出「未來 7 或 30 天內可**淨賺 5%**」
機率最高的標的。所有門檻都已扣除手續費、證交稅與滑價 —— 個股實際要漲 **5.83%** 才淨賺 5%。

不架站、不開 port，整套包在一個 Docker image 裡，`data/` 目錄帶著走就等於帶著全部歷史。

## 用法

```bash
docker compose build
docker compose run --rm --entrypoint python forecast test_run.py  # 自我檢查
docker compose run --rm forecast fetch                            # 股價（首次約 3 分鐘）
docker compose run --rm forecast chips                            # 籌碼面（首次約 10 分鐘）
docker compose run --rm forecast backtest --horizon 7             # 回測，看有沒有搞頭
docker compose run --rm forecast daily --horizon 7                # 今日候選清單
```

`chips` 可以重複跑，每次只補缺的部分。免費額度中斷後重跑同一個指令即可接續。

自選股寫在 `data/watchlist.txt`，一行一檔。這些標的即使成交量排不進前 300 也一定納入。

參數用環境變數覆寫，例如手續費 6 折、放寬停損：

```bash
docker compose run --rm -e BROKER_DISCOUNT=0.6 -e STOP_LOSS=0.12 forecast backtest --horizon 7
```

帶著走：`docker save -o forecast.tar stock-forecast`，或直接帶 repo 到別台機器 build。

## 目前的實測結果（2020-09 ~ 2026-09，300 檔，13 折 walk-forward）

### H=7d

| 引擎 | precision@20 | 全市場 lift | **同波動 lift** | picks 波動分層 | 平均淨報酬/筆 |
|---|---|---|---|---|---|
| 規則排序 | 44.6% | 1.53x | 1.06x | 7.8 | −0.46% |
| ML 純價量 | 45.9% | 1.58x | 1.06x | 8.1 | −0.41% |
| ML 價量+籌碼 | 46.6% | 1.60x | 1.07x | 8.2 | −0.39% |
| **ML 波動率中性化** | 37.8% | 1.27x | **1.16x** | 4.7 | −0.34% |

### H=30d

中性化後同波動 lift 只剩 **1.05x**（85% 的折數 > 1.0）。**30 天版本沒有真正的選股能力。**

---

### 為什麼要看「同波動 lift」

全市場 lift 拿所有股票當分母。但高波動股本來就比較容易在 7 天內摸到 ±5%，
所以「專挑波動大的股票」會被誤算成選股能力。

同波動 lift 改拿**同一天、同波動率分層**的股票當對照組（10 層，leave-one-out
避免把自己算進自己的基準），問的是：「在波動率相當的同儕裡，你挑得比較準嗎？」

差距非常大：

```
ML 價量+籌碼    全市場 lift 1.60x  ->  同波動 lift 1.07x
```

**表面優勢有 95% 只是「挑到波動大的股票」**，picks 平均落在波動率第 8.2 分層（0–9）。
這也解釋了先前「precision 遠高於 base rate、期望值卻是負的」的矛盾：
高波動股更容易觸到 +5.83%，但同樣更容易觸到 −5%。

中性化的做法是把每日分數對「波動率百分位」做橫斷面迴歸取殘差
（用百分位而非原始值，因為波動率右尾很長，原始值會讓少數暴走股主導迴歸線）。
中性化後 picks 移到第 4.7 分層，precision 從 46.6% 掉到 37.8%，
但同波動 lift 升到 **1.16x，且 13 折全部 > 1.0**。

**結論：確實有真正的選股能力，只是先前被波動率蓋住了。**
1.16x 每折都成立，比 1.60x 裡 95% 是雜訊可信得多。

### 但期望值還是負的

停利/停損的幾何沒變：要 +5.83% 才贏、−5% 就輸，勝率必須 **53.3%** 才打平。
中性化後的 37.8% 離這個門檻很遠，所以每筆仍然 −0.34%。

真正的障礙不是模型，是**「7 天內淨賺 5%」這個目標對上 5% 停損太苛刻**。
1.16x 的真實選股能力補不上 37.8% 到 53.3% 的差距。要讓它轉正，只有三條路：

1. **降低停利目標**（例如淨 2–3%）—— 但這偏離你原本的需求
2. **調整停利/停損比例** —— 見下方敏感度測試
3. **把同波動 lift 做到 ~1.5x** —— 需要的是全新的資訊源，不是現有特徵再加工

### 停損敏感度測試（H=7，中性化引擎）

| 停損 | precision@20 | 同波動 lift | 折數 > 1.0 | 平均淨報酬/筆 | 最大回撤 |
|---|---|---|---|---|---|
| 3% | 29.4% | 1.11x | 85% | −0.50% | −18.7% |
| 5% | 37.8% | 1.16x | **100%** | −0.34% | −15.3% |
| 8% | 44.2% | 1.18x | **100%** | −0.21% | −13.7% |
| 12% | 47.8% | 1.19x | **100%** | **−0.03%** | −11.3% |

兩件事值得注意：

1. **同波動 lift 在 5–12% 停損之間穩定在 1.16–1.19x。** 選股能力不隨參數飄移，
   所以它不是掃參數掃出來的假象 —— 這跟「從一堆結果裡挑最好的那格」是不同性質的證據。
2. **停損放越寬，最大回撤反而越小**（−18.7% → −11.3%）。緊停損在 7 天的尺度上
   會被雜訊反覆掃出場。

但即使停損放到 12%，期望值也只是 −0.03%，剛好打平。

**結論：現在不要拿真錢下去跑。** 選股能力是真的，但太小，補不上
「7 天淨賺 5%、停損 5%」需要的 53.3% 勝率。要讓它轉正，該動的不是參數而是資訊源 ——
目前 20 個特徵全部由 OHLCV 與籌碼面衍生，這兩類公開資料的邊際訊息大概就到這裡了。

## 架構

| 檔案 | 職責 |
|---|---|
| `config.py` | 費率、門檻、股票池參數。`raw_target()` 把淨報酬反解成毛漲幅 |
| `data.py` | TWSE/TPEx OpenAPI 選股票池 + yfinance 抓價 + SQLite |
| `chips.py` | 籌碼面：三大法人買賣超、融資券餘額（兩條取得路徑，見下） |
| `model.py` | 特徵、triple-barrier 標籤、規則排序、ML 分類器 |
| `backtest.py` | Walk-forward（含 embargo）、precision@N / lift / 資金曲線 |
| `run.py` | CLI：`fetch` / `backtest` / `daily` |
| `test_run.py` | 守住兩個會安靜出錯的地方：金錢計算、資料洩漏 |

兩個刻意的設計：

- **訊號在 t 日收盤產生，進場價用 t+1 日開盤**，不是當日收盤。否則是前視偏誤。
- **訓練集尾端砍掉 horizon+1 天（embargo）**。標籤用到未來 H 天的價格，不砍掉的話
  測試期資訊會滲進訓練集，回測數字會漂亮到假。`test_run.py` 有斷言守著。
- **籌碼買賣超一律除以同期成交量**，變成「法人吃掉幾 % 的成交量」。用絕對股數的話
  台積電永遠輾壓小型股，橫斷面排序就沒有意義了。
- **籌碼缺資料留 NaN，不填 0**。0 會被模型當成「法人剛好沒買」的真實訊號。
  HistGradientBoosting 原生吃 NaN，不需要補值。
- **排序做波動率中性化，基準用同波動分層**。不做的話，「挑波動大的股票」
  會被誤算成選股能力（實測會把 1.07x 的真實優勢膨脹成 1.60x）。
  `daily` 輸出的就是中性化後的排序。

### 籌碼面的兩條取得路徑

| 路徑 | 用途 | 成本 |
|---|---|---|
| FinMind（預設） | 一次性歷史回補：一檔一請求拿全歷史 | 300 檔 = 602 次請求 |
| 證交所/櫃買 OpenAPI（`--source official`） | 每日增量：一請求拿全市場當日 | 一天 4 次請求 |

兩者已交叉驗證：2330 與 6488 的融資餘額、融券餘額、外資與投信買賣超四個數字完全一致。

**不要用官方 API 做密集歷史回補。** 連續數百次請求後證交所會回 HTTP 307 轉址到
「因為安全性考量，您所執行的頁面無法呈現」，而 `requests` 預設跟隨轉址會拿到 200 + HTML，
錯誤被靜默吞掉，只看到程式莫名變慢。`chips.py` 的 `_get` 已關掉轉址並把 3xx 當成被擋。

FinMind 免費額度（未登入）約 300 次/小時，跑到一半會中斷 —— 這是正常中斷點，
重跑同一個指令會從缺口接續。要一次跑完就去 finmind.github.io 註冊免費 token：

```bash
docker compose run --rm -e FINMIND_TOKEN=xxx forecast chips
```

每日結果同時寫入 `data/signals/` 的 CSV 與 DB 的 `signals` 表，三個月後可以用真實價格
回頭驗證線上表現，而不是只信回測。

要每天自動跑就用 host 的 crontab 呼叫 `docker compose run`，容器裡不塞 cron。
